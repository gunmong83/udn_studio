## 후속 수정 상태

- 결제 승인·취소를 라이브 비밀키 필수로 변경하고 테스트 키 fallback을 제거했다.
- 가상계좌는 입금 웹훅 없이 결제 완료로 저장되지 않도록 결제수단에서 제거했다.
- 관리자 주문 상태 전이를 제한하고, 환불 상태 변경은 토스 취소 성공 후에만 기록하도록 변경했다.
- 결제 기록이 있는 주문의 물리 삭제를 막고, 승인·취소 저장을 조건부 원자 전환으로 보강했다.
- 관리자 권한을 이메일 문자열뿐 아니라 DB 사용자 ID와 함께 확인하고, 관리자 이메일의 공개 가입을 차단했다.
- 보안 헤더, Docker 비밀 파일 제외, Toss 공개키의 이미지 빌드 전달 및 라이브 키 CI 사전검사를 추가했다.
- 로컬 `scripts/test-local.ps1 -SkipInstall`(lint + production build) 및 TypeScript 검사를 통과했다.
- 남은 운영 전제: GitHub Actions secret `NEXT_PUBLIC_TOSS_CLIENT_KEY`는 실제 `live_ck_...` 값이어야 하며, Lightsail `/opt/udn_studio/.env.production`의 `TOSS_SECRET_KEY`도 실제 `live_sk_...` 값이어야 한다. 값이 없거나 placeholder이면 CI가 배포를 중단한다.

## 확인된 긍정적인 부분

- 주문 API는 클라이언트의 가격을 사용하지 않고 상품 데이터의 가격과 서버 배송비 계산을 사용한다. 상품별 수량은 정수 1~99로 제한한다.
- 고객 주문 조회/취소는 `userId`로 소유권을 제한한다. 기본 배송지는 세션 사용자에게만 연결된다.
- 운영 비로그인 요청: `/api/orders`, `/api/profile` 401, `/api/admin/orders`, `/api/admin/members` 403. 이는 비로그인 차단 확인이며 로그인 사용자 간 격리 실증은 아니다.
- 비밀번호는 랜덤 salt + scrypt 해시로 저장하고 timingSafeEqual로 비교한다. 평문 저장은 발견하지 않았다.
- 고객의 결제 취소 요청에는 주문별 Idempotency-Key가 있다.
- HTTP→HTTPS 301 확인. curl로 확인한 응답은 `Server: cloudflare`, `CF-RAY`, `cf-cache-status: DYNAMIC`. DNS NS도 Cloudflare이다. WAF 규칙·SSL 모드·원본 서버 차단까지 검증했다는 의미는 아니다.
- 공개 `/.env`, `/prisma/dev.db` 경로는 404. 모든 비밀/백업 경로의 비노출을 보장하는 검사는 아니다.

## 우선 수정: P1

### 1. 가상계좌 발급을 결제 완료로 저장

- 근거: `web/app/checkout/page.tsx:442`에서 가상계좌 선택 제공. `web/app/api/payments/confirm/route.ts:88` 이후 성공 응답의 status 확인 없이 PAID로 저장.
- 토스 가상계좌 승인 성공은 입금 완료가 아니라 WAITING_FOR_DEPOSIT일 수 있다. 현재 코드에는 입금 웹훅 수신 경로가 없고 DB에도 입금 대기 상태가 없다.
- 영향: 돈을 받기 전에 결제 완료 안내/관리자 알림/출고 대상으로 처리될 수 있다. 계약상 가상계좌가 활성화된 경우의 위험이다.
- 권고: 우선 가상계좌 제공을 중지하거나, 입금 대기·만료·입금취소와 검증된 웹훅 및 재조회 처리를 구현. DONE, orderId, amount, paymentKey를 검증한 뒤 결제 완료로 전환.
- 검증: 발급 직후 UNPAID/입금대기 유지, 입금 후 한 번만 PAID, 중복/위조/순서가 뒤바뀐 웹훅, 입금취소, 만료, 환불계좌 필요 시나리오.
- [토스 가상계좌 연동](https://docs.tosspayments.com/guides/v2/payment-window/integration-virtual-account)

### 2. 관리자 화면의 환불은 실제 환불을 실행하지 않음

- 근거: `web/app/admin/page.tsx:566`~에서 CANCELLED/REFUNDED 선택 가능. `web/app/api/admin/orders/route.ts:34`는 전달받은 status를 그대로 DB에 저장하고 토스 취소 API를 호출하지 않는다.
- 영향: 관리자는 환불 완료로 표시했지만 고객 돈은 환불되지 않는 상태가 생긴다. 미결제 주문을 PAID/출고 상태로 변경하는 것도 허용된다.
- 권고: 배송 상태 변경과 금전 취소 작업을 분리. 서버에서 허용된 상태 전이만 검증하고, 환불 성공/재조회 확인 후 금전 상태를 기록. 변경 담당자·시각·사유·PG 응답 식별자를 감사 기록으로 저장.
- 검증: 미결제→배송준비 거부, 환불 API 실패 시 완료 표시 금지, 중복 취소, 취소 후 출고 거부.

### 3. 승인·취소·출고·삭제 사이 동시성 보호 부족

- 근거: confirm route의 조회 후 무조건 update; cancel route의 상태 조회 후 외부 API 호출 및 update; admin PATCH의 무조건 update. confirm은 CANCELLED 주문의 승인을 막지 않는다.
- 영향: 취소 중 출고, 취소된 미결제 주문이 뒤늦게 PAID로 복귀, PG 승인 성공 뒤 DB 오류로 주문 상태 불일치가 발생할 수 있다. 정상 화면 한 번 클릭 테스트로는 확인하기 어려운 경쟁 조건이다.
- 권고: 조건부 원자적 상태 전환, 승인/취소 진행 상태, 작업 식별자, PG 조회 기반 복구 절차. 네트워크 타임아웃은 확정 실패와 구별. 정기 결제 대사 필요.
- 검증: 승인과 취소, 취소와 PREPARING, 승인과 삭제를 동시에 실행하는 격리 테스트 및 PG 성공 직후 DB 실패 주입.
- [OWASP 거래 상태 전이 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)

### 4. 환불 기록도 삭제 가능

- 근거: `web/app/api/orders/route.ts:81`은 paymentStatus가 PAID일 때만 DELETE를 거부한다. REFUNDED이면 삭제 가능하며 OrderItem은 cascade 삭제된다. 결제 실패 페이지도 orderId에 대해 DELETE를 호출한다.
- 영향: 환불된 주문·상품 기록이 사라져 고객 응대 및 정산 근거를 잃는다. 승인 중인 UNPAID 주문 삭제도 경쟁 조건을 만든다.
- 권고: 금전 거래가 시작된 주문의 물리 삭제 금지. 결제 실패/취소 상태를 보존하고, 목록 숨김과 법정 보관/파기를 별도 설계.

### 5. 이메일 미인증 가입과 이메일 문자열 기반 관리자 권한

- 근거: `web/app/api/register/route.ts:17`은 메일 소유 확인 없이 계정을 만든다. `web/src/auth.ts:49`, `web/src/lib/admin.ts:14`는 이메일 일치만으로 관리자 권한을 준다.
- 영향: 관리자 이메일이 DB에 아직 없다면 제3자가 그 이메일로 일반 가입 후 관리자 권한을 얻을 수 있다. 이미 정상 관리자 계정이 있으면 unique 제약으로 이 신규가입 경로는 차단되므로, 현재 계정 탈취가 입증된 것은 아니다. 일반 사용자 메일 사칭/선점도 가능하다.
- 권고: 관리자는 검증된 사용자 ID와 별도 역할로 명시 등록하고 공개 회원가입에서 관리자 역할 생성 금지. 일반 가입 이메일 인증, 관리자 재인증/2FA, 세션 회수 체계.
- [OWASP 이메일 검증](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)

### 6. 운영 결제 번들에 테스트 클라이언트 키

- 근거: 운영 `/checkout`이 참조하는 JS를 검사했을 때 `test_ck_` 존재, `live_ck_` 없음. `web/src/lib/toss.ts:70`은 NEXT_PUBLIC_TOSS_CLIENT_KEY 없으면 테스트 키를 쓴다. Docker 빌드에 이 공개 환경변수를 전달하는 단계가 없다.
- 영향: 현재 공개 결제 화면을 실결제 설정으로 볼 수 없다. 서버 시크릿이 라이브일 경우 키 불일치도 발생할 수 있다. 서버 비밀키 실제 값/모드는 이번에 읽지 않았다.
- 권고: 테스트 모드를 명시적으로 구분하고 라이브 모드에서 키 누락은 배포 실패 처리. NEXT_PUBLIC 값은 빌드에 반영해야 하므로 컨테이너 런타임 환경값만 교체하는 것으로 충분하지 않다. 프런트/서버의 상점·모드 일치 확인 후 별도 라이브 승인·취소 검증.
- 공개 샘플 테스트 시크릿 상수도 존재하지만 이를 실제 라이브 비밀키 유출로 판정하지 않는다.
- [토스 API 키](https://docs.tosspayments.com/reference/using-api/api-keys)

## 추가 보완: P2

1. **약관 동의 증빙 없음**: signup의 checkbox는 브라우저에서만 검사하고 API에 전송하지 않는다. User 스키마에 동의 버전/시각이 없다. 로그인 화면 OAuth로 신규 계정 생성 시 사이트 동의 단계를 거치지 않는다. 신규 계정은 서버 측 동의 저장 후 활성화해야 한다.
2. **요청 남용 제한 없음**: 코드에서 로그인/가입/주문 생성 rate limit, 요청 크기·items 수 제한을 찾지 못했다. 주문 하나의 quantity 제한만으로는 여러 항목/반복 요청을 막지 못한다. Cloudflare 사용자 지정 규칙은 미검증. 계정/IP별 제한, 입력 상한, 중복 상품 병합과 총액 범위 검증 필요.
3. **한정수량 재고 미관리**: 상품에 100부 한정 표시가 있으나 서버 재고 예약/차감이 없다. 다른 판매 채널과 함께 판매하면 초과 판매 가능. 콘텐츠 DB화와 별개로 판매 가능 수량 또는 운영 품절 통제가 필요하다.
4. **보안 헤더/CSRF 보강**: 확인한 운영 응답에 CSP, HSTS, X-Frame-Options가 없다. 커스텀 변경 API에 Origin/CSRF 검증이 없으며 JSON Content-Type을 강제하지 않는다. Auth.js 자체 보호와 커스텀 API 보호는 별개. 현재 쿠키 정책을 우회하는 공격을 입증한 것은 아니다. 결제/주소검색 외부 스크립트와 호환되는 정책을 먼저 검증해야 한다.
5. **Docker 비밀 파일 제외 규칙 불충분**: `.dockerignore`에 `.env*` 제외가 없고 `docker/Dockerfile:11`에서 web 전체를 빌드 단계로 복사한다. 현재 git 추적 대상에 실제 env 파일은 없어서 이번 CI 이미지의 비밀 노출을 확인한 것은 아니다. 로컬 Docker 빌드 시 비밀 파일이 빌드 컨텍스트/레이어에 포함될 위험을 제거해야 한다.
6. **공급망/런타임 축소**: npm ci 대신 npm install --legacy-peer-deps를 사용해 빌드에서 의존성이 달라질 수 있다. 개발 의존성까지 런타임 이미지로 복사하며 USER 지정이 없다. lockfile 고정 설치, 운영 의존성만 포함, 비root 실행 필요.
7. **의존성 경고**: 로컬 package-lock을 npm 보안 advisory API로 조회한 결과 개발 의존성 braces 3.0.3에 High 경고 GHSA-vfj7-8cjw-p6xm가 있었다. 실제 서비스 경로에서 공격자 입력이 해당 함수에 도달하는지는 미확인이고 Docker npm install 결과와도 대조 필요. [공식 advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm).
8. **운영 복구**: 배포 스크립트는 새 컨테이너 건강 확인 전에 이전 컨테이너를 삭제한다. 실패 시 자동 rollback이 없다. start.sh는 migrate 실패 시 db push로 대체한다. SQLite 외부 볼륨은 유지되지만 저장소에서 자동 백업/복원 검증을 찾지 못했다. 실제 서버 백업 유무는 미확인이다.
9. **결제 알림 유실 가능**: 메일 전송은 비동기로 호출하고 실패는 로그만 남긴다. 미설정이면 조용히 종료한다. 재시도 가능한 알림 큐/발송 이력과 관리자 대시보드가 필요하다.
10. **정책/사업자 표시**: 운영 footer에서 사업자 상세와 약관/개인정보 상시 링크가 보이지 않았다. 현재 정책은 보유기간·수탁자·반품 비용/절차 등이 구체적이지 않은 요약문이다. 실제 사업자와 배송/PG 계약 정보를 확인한 뒤 문서와 동의 항목을 완성해야 한다. 이번 검토는 법적 적합성 판정이 아니다.

| 회원가입 동의 누락 | 화면 동작 통과 | 동의 안내 표시. 서버 검증은 위와 같이 없음 |
| 약관 페이지 열기 | 통과 | 실제 약관 페이지로 이동 |
| 결제 중 로그인 후 복귀 | 코드상 문제 | callbackUrl=/checkout 전달하지만 login은 항상 /로 이동 |
| 비밀번호 찾기 | 미구현 | 로그인 UI/라우트에서 복구 기능 없음 |
| 결제 실패 재시도 | 위험 | 실패 안내로 재결제를 유도하기 전에 PG 승인 여부 재확인 필요 |
| 배송비 안내 | 개선 필요 | 장바구니의 합계 20,000원에 배송비 제외라는 설명이 없음. 서버 정책은 기본 4,000원/500,000원 이상 무료 |
| 로그인 네트워크 오류 | 코드상 문제 | loginWithPassword/OAuth에 catch/finally가 없어 로딩 상태가 유지될 수 있음 |
| 가입 입력 중 약관 확인 | 개선 필요 | 같은 탭에서 이동하며 입력값 보존 수단 없음 |
| 마이페이지 우편번호 검색 | 배포 포함 확인 | 인증된 상태의 팝업 선택·DB 저장까지는 이번에 실행하지 않음 |

실제 OAuth 계정 생성/연동, 휴대기기 결제 앱 복귀, 주소 팝업 차단, 실승인·환불, 배송준비 이후 고객 취소 거부는 별도 테스트가 남아 있다. 따라서 전체 사용자 여정 통과로 표현하면 안 된다.

## 권장 수정 순서와 완료 기준

1. 관리자 권한 부여와 가상계좌·환불 처리 P1 수정. 테스트/라이브 키 누락 검증 추가.
2. 승인·취소·출고 상태 전이를 한 정책으로 관리하고 결제 기록 삭제 금지. PG 결과와 DB 상태 복구/대사 구현.
3. 격리 DB와 모의 PG에서 금액 변조, 타인 주문, 중복 요청, 동시 요청, 네트워크 오류, DB 실패를 검증.
4. 토스 테스트 상점에서 실제 테스트 승인/취소 및 웹훅 검증. 라이브 전환은 같은 상점 키 확인 후 승인·취소·PG 대시보드·DB·알림 대조.
5. 약관 증빙/입력 제한/보안 헤더/백업 복원/배포 rollback과 사용자 흐름 개선을 묶어 다음 릴리스.

검토 기준: [OWASP API Security](https://owasp.org/projects/api-security-project), [객체 소유권 검증](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/), [토스 결제 연동](https://docs.tosspayments.com/guides/v2/payment-window/integration), [토스 웹훅](https://docs.tosspayments.com/guides/v2/webhook). 일반적인 전자상거래 위험과 실제 코드의 대응을 비교했으며, 특정 타사 침해 사고가 이 사이트에서도 발생했다고 주장하는 내용은 없다.
