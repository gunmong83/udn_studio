# 회원가입 인증 및 배송 시작 알림톡

## 현재 네이버클라우드 템플릿

2026-10-14에 Naver Cloud SENS 콘솔의 `homepage_katalk_alarm` 서비스, 카카오 채널 `@studioudn`에 아래 템플릿을 등록했다.

- 템플릿 코드: `UDNSHIPSTART`
- 템플릿 이름: `studioUDN_배송시작_운송장안내`
- 카테고리: 배송 → 배송상태
- 메시지 유형/강조 유형: 기본형
- 버튼: 웹 링크 `배송 조회`
- 모바일·PC 버튼 URL 형식: `https://#{배송조회URL}`
- 보안 설정: 미설정
- 2026-10-14 콘솔 재확인: 템플릿 상태 `등록 완료`, 검수 상태 `완료`

회원가입 템플릿 `UDNSIGNUPVERIFY` (`studioUDN_회원가입_휴대폰인증`)도 같은 콘솔에서 `등록 완료 / 완료`로 확인했다. 보안 설정은 설정이며, 버튼은 없다. 본문과 버튼을 변경하면 재검수가 필요할 수 있으므로 승인 내용을 임의로 바꾸지 않는다. 동일한 코드를 가진 템플릿을 중복 등록하지 않는다.

## 등록한 본문

```text
[studioUDN]
주문하신 상품의 배송이 시작되었습니다.

택배사: #{택배사}
송장번호: #{송장번호}

아래 배송 조회 버튼을 눌러 배송 현황을 확인해 주세요.
```

검수 문의란에는 결제가 완료된 주문을 관리자가 출고 처리하면서 택배사와 송장번호를 입력한 뒤, 주문자에게 배송 시작과 택배사별 조회 링크를 안내하는 정보성 알림이라는 점을 설명했다.

## 회원가입 인증 승인 본문

```text
[studioUDN]
회원가입을 위한 휴대폰 인증번호를 안내드립니다.

인증번호: #{인증번호}

인증번호를 3분 이내에 회원가입 화면에 입력해 주세요.
본인이 요청하지 않았다면 이 메시지를 무시해 주세요.
```

## 사이트 연동 규칙

- 연동 코드는 `web/src/lib/sens-alimtalk.ts`, 회원가입 인증 API, 관리자 주문 API에 구현되어 있다. 코드 변경과 운영 배포 완료는 구분해야 한다.
- 관리자가 배송 상태를 `배송중`으로 바꾸고 택배사와 송장번호를 저장할 때 주문 고객에게 한 번만 발송한다. 중복 저장이나 재시도 때문에 중복 알림이 가지 않도록 서버에서 발송 결과/멱등성을 관리한다.
- 발송 본문의 치환값은 `#{택배사}`와 `#{송장번호}`다. 값은 서버에서 검증하고, 고객이 직접 입력한 값을 그대로 신뢰하지 않는다.
- 콘솔의 변수 `#{배송조회URL}`에는 프로토콜을 제외한 호스트와 경로가 들어간다. SENS 발송 API는 변수 사전을 받는 방식이 아니라 **치환이 끝난 본문과 완전한 버튼 URL**을 받는다. 따라서 API의 `linkMobile`·`linkPc`에는 `https://`가 한 번 포함된 전체 URL을 전달한다. 두 방식을 혼동하지 않는다.
- 택배사별 조회 URL은 서버에서 허용된 택배사 목록으로 생성한다. 택배사 이름과 송장번호를 URL 문자열로 단순 결합하지 말고, 각 택배사의 공식 조회 규칙과 인코딩을 적용한다. 지원되지 않는 택배사나 잘못된 송장번호는 발송 전에 오류로 처리한다.
- 지원 택배사는 CJ대한통운·우체국·한진·롯데·로젠·경동·일양이다. 일양은 확인 가능한 공식 조회 입력 페이지로 연결하므로 수신자가 알림톡의 송장번호를 페이지에 직접 입력한다. 검증되지 않은 직접 조회 URL을 추측해 추가하지 않는다.
- 우체국은 공식 `https://service.epost.go.kr/iservice/usr/trace/usrtrc001k01.jsp` 조회 폼의 GET action인 `https://service.epost.go.kr/trace.RetrieveDomRigiTraceList.comm?sid1=<숫자 13자리>`로 직접 조회한다. 2026-10-14 공식 HTML과 테스트 번호 응답에서 확인했다. `RetrieveDomRcvTraceList`는 잘못된 경로이며, JSP 입력 페이지에 파라미터만 붙이는 방식도 자동 입력을 보장하지 않으므로 사용하지 않는다. 알림톡 모바일·PC 버튼과 사이트 배송조회가 같은 공통 URL 생성기를 사용한다. 이미 발송된 알림톡 링크는 코드 변경으로 수정되거나 자동 재발송되지 않는다.
- 메시지 본문과 버튼 정보는 카카오가 승인한 템플릿과 정확히 일치해야 한다. 사이트 연동에서는 등록된 템플릿 코드 `UDNSHIPSTART`와 동일한 버튼 이름·유형·변수 위치를 사용한다.
- 알림톡은 고객이 요청한 주문/배송 상태 안내에만 사용한다. 광고나 홍보 문구를 섞지 않는다.
- 모든 비밀키와 발신 설정은 환경 변수/서버 설정으로 관리하며 저장소에 기록하거나 커밋하지 않는다.
- 이메일 가입과 신규 Google/네이버 가입 모두 휴대폰 인증 증명을 서버에서 일회용으로 소비하고 `User.phoneVerifiedAt`을 저장한다. 코드 유효기간은 3분, 인증 후 가입 완료까지는 15분이다. 번호 변경·재인증·증명 재사용은 서버에서 검증한다.
- 인증 완료 후에는 인증번호 발송·재인증 버튼을 숨기고 인증된 번호와 완료 안내만 표시한다. 15분이 지나 인증 증명이 만료된 경우에만 인증 입력 흐름을 다시 표시한다.
- 재전송은 번호별 60초 간격·시간당 5회, IP별 시간당 10회다. OTP·증명은 HMAC 해시만 DB에 저장하며, 인증번호를 API 응답이나 로그에 출력하지 않는다. 소비한 인증기록도 24시간 정리 대상까지 남겨 발송 제한이 가입 성공으로 초기화되지 않게 한다.
- 배송은 결제 완료(`paymentStatus=PAID`) 주문이 `상품 준비중`에서 `배송중`으로 변경될 때만 최초 요청한다. 택배사와 송장번호는 같은 저장 시점의 최종 값으로 검증한다. 형식 검증은 실제 송장 발급 여부를 보장하지 않으므로 관리자가 실물 송장을 대조해야 한다.
- 관리자 편집에서 `상품 준비중`은 상태만 저장하고 택배사·운송장 입력란을 숨긴다. 숨겨진 배송 입력값은 요청에 포함하지 않는다. 배송중·배송 완료에서는 배송 입력란을 표시하며, 배송중 저장 시 필수 검증과 알림톡 발송 규칙을 유지한다.
- 우체국으로 최초 배송중 전환하거나 배송중 송장정보를 변경하면 `epost-verification.ts`에서 명세서의 국내우편물 종적조회 OpenAPI를 호출해 `successYN=Y`, `returnCode=00`, 응답 등기번호 일치를 확인한다. 조회 결과 없음은 422, 키 누락·API 오류·시간초과·응답형식 변경은 503으로 DB 저장과 알림톡 발송을 막는다. API 요청 시간 제한은 10초다. 응답에서 발송인/수취인 개인정보는 추출하거나 저장하지 않고, 이벤트의 날짜·시간·위치·처리현황만 화면 표시 목적에 사용한다. 상품 준비중·같은 배송정보 반복 저장·알림톡 재시도에는 불필요한 조회를 하지 않는다. 타 택배사는 기존 형식 검증만 수행한다.
- 관리자 주문 카드의 `우체국 배송상태 확인` 버튼과 시간별 폴링은 배송중인 우체국 주문의 최신 `dlvySttus` 및 종적(`processSttus`, 처리일시, 위치)을 주문에 저장해 관리자와 고객의 주문 추적 화면에 표시한다. 매 회차 최신 상태를 갱신하되, 최종 `배달완료`일 때만 주문을 배송 완료로 자동 변경하며 완료된 주문은 이후 조회에서 제외한다. 배송완료 알림은 발송하지 않는다. 관리자가 편집창에서 직접 `배송 완료`를 선택해 저장할 때도 같은 API 확인을 거쳐 `배달완료`일 때만 저장한다.
- 공식 명세는 국내등기 13자리 번호를 입력받고 XML로 결과를 반환한다고 설명한다. 명세의 전송 암호화 항목에는 SSL이 선택되어 있지 않고 예시 URL도 HTTP다. 현재 구현은 명세에 맞춰 HTTP API를 사용하므로 `EPOST_SERVICE_KEY`가 TLS로 보호되지 않은 연결을 통해 전달된다. 키는 로컬 `web/.env.local` 및 운영 서버 `/opt/udn_studio/.env.production`에만 설정하고 코드·Git·로그에 남기지 않는다. 호출 인증키는 `EPOST_SERVICE_KEY` 환경 변수로 읽는다.
- API 조회 성공은 번호에 대한 우체국 종적 데이터가 있다는 뜻이며 주문의 수취인/실물 송장과 일치한다는 보장은 아니다. 실제 발급 송장과 수령인을 관리자가 대조해야 한다. API 원문이나 발송인/수취인 정보를 로그에 남기지 않는다.
- `ShipmentNotification.orderId`는 유일하다. `READY → SENDING → ACCEPTED → SENT/FAILED`로 기록하고 요청번호·메시지번호를 저장한다. SENS `202`/`A000`는 접수 성공이며, `0000` 수신 결과까지 조회해야 수신 성공이다. 관리자 화면 새로고침 시 미확정 결과를 조회한다.
- 반복 저장은 재발송하지 않는다. `FAILED`/`READY` 기록만 관리자 `알림톡 재발송` 버튼으로 다시 요청한다. 타임아웃·서버 오류·프로세스 중단처럼 접수 여부를 알 수 없는 경우는 `UNKNOWN`으로 남기고 자동 재전송을 막는다. 이 경우 SENS 콘솔에서 요청을 확인한 후 운영자가 기록을 대조해야 한다. 이미 접수된 배송정보는 저장으로 변경할 수 없다.
- 배포 전부터 배송중인 기존 주문은 일괄 발송하거나 반복 저장 시 새 알림을 만들지 않는다.
- 회원 탈퇴 시 주문 원장은 기존 정책대로 익명화하고 연관 배송 알림기록은 삭제한다.
- SMS 대체 발송은 명시적으로 `false`다. 켜려면 SENS 채널의 대체 SMS와 사전 등록 발신번호를 별도로 설정·검증한 후 구현한다.

## 환경 변수 및 DB 적용

로컬은 `web/.env.local`, 운영은 서버의 `/opt/udn_studio/.env.production`에 설정한다. API 키를 코드·GitHub 저장소·문서에 넣지 않는다. 자동 조회에는 임의 생성한 긴 비밀값을 운영 환경의 `EPOST_POLLING_TOKEN`과 GitHub 저장소 Actions secret `EPOST_POLLING_TOKEN` 양쪽에 동일하게 설정한다. 토큰은 저장소에 기록하지 않는다. 운영 서버 환경변수를 변경한 뒤에는 컨테이너 재시작/배포가 필요하다. Actions 스케줄은 GitHub의 부하에 따라 시작이 지연될 수 있으므로 정확한 시각이 중요한 경우에는 Lightsail의 systemd timer가 대안이다.

```dotenv
SENS_ALIMTALK_SERVICE_ID=ncp:kkobizmsg:kr:112583704463198:homepage_katalk_alarm
SENS_ALIMTALK_CHANNEL_ID=@studioudn
SENS_ACCESS_KEY=<NCloud access key>
SENS_SECRET_KEY=<NCloud secret key>
```

Biz Message 서비스 ID는 SMS 서비스 ID와 다르다. 발송 서명은 요청 메서드·정확한 URI·타임스탬프·Access Key를 HMAC SHA-256으로 서명한다. 템플릿 코드는 승인된 두 코드로 소스에서 고정한다. 키 변경 후 서버를 재시작해야 한다.

DB에는 `PhoneVerificationChallenge`, `ShipmentNotification`, `User.phoneVerifiedAt`이 필요하다. 로컬 SQLite 초기화는 `scripts/init-local-db.mjs`가 추가 필드를 적용한다. 현재 Docker 시작 스크립트는 마이그레이션 이력이 없을 때 `prisma db push --skip-generate`를 실행한다. 배포 전 DB 백업을 유지하고 데이터 삭제 옵션은 추가하지 않는다.

## 테스트 절차

주소 검색은 `PostcodeSearch` 공통 컴포넌트의 iframe `embed()`로 결제·회원가입·마이페이지에 표시한다. 내장 브라우저의 새 팝업 차단을 피하기 위해 `window.open` 방식을 다시 넣지 않는다. 카카오 우편번호 SDK는 페이지 프로토콜을 따르므로 HTTP 로컬 개발에서는 `http://postcode.map.kakao.com` 프레임을 개발 환경 CSP에만 허용한다. 운영은 HTTPS 프레임 정책을 유지한다.

### 자동 테스트 (실발송·과금 없음)

저장소의 `web` 폴더에서:

```powershell
pnpm exec prisma generate
node --test tests/alimtalk.test.cjs
pnpm build
```

자동 테스트는 새 임시 SQLite DB와 실제 API 핸들러를 사용하되, SENS·메일·결제 호출을 가짜 응답으로 대체한다. `.env`를 읽지 않고 고객·운영 DB를 사용하지 않는다. 승인 본문/서명, 이메일·OAuth 인증 우회 차단, OTP 만료/오입력/재사용/동시 요청, 배송정보 누락/형식/미결제 차단, 중복 발송/명시적 재시도/불명확한 접수 보호를 확인한다.

### 실제 수신 테스트 (알림톡 발송 비용 발생)

1. 로컬에 위 4개 환경 변수를 설정하고 DB를 적용한 뒤 개발 서버를 시작한다. SENS에 별도 무료 샌드박스가 있다고 가정하지 않는다. 실발송에는 실제 서비스와 승인 템플릿을 사용한다.
2. 본인이 관리하는 휴대폰 번호로 `/signup`의 이메일 가입 또는 신규 소셜 가입 화면에서 `인증번호 받기`를 누른다. 카카오톡 수신·3분 이내 인증·가입 완료를 확인한다. 오입력, 재전송 제한, 인증 전 가입 불가도 확인한다. 카카오톡을 사용할 수 없는 번호는 현재 SMS로 자동 대체되지 않는다.
3. 배송 테스트는 **본인 번호를 가진 테스트 주문**으로만 진행한다. 운영의 실제 고객 주문을 테스트 용도로 변경하지 않는다. 정상 결제된 테스트 주문을 관리자에서 `상품 준비중`으로 변경한다.
4. 택배사 누락·송장 누락·짧은 번호는 저장이 차단되는지 확인한다. 실제 발급된 송장번호와 택배사를 입력하고 `배송중`으로 저장한다. 받은 알림톡의 택배사·송장·배송 조회 버튼을 확인한다.
5. 동일한 배송정보를 다시 저장해도 두 번째 알림이 오지 않는지 확인한다. 관리자 새로고침 후 `수신 성공`, SENS `AlimTalk Message`의 수신 결과 `0000`을 함께 확인한다.
6. 실패 시 먼저 콘솔의 요청/수신 오류와 환경 변수를 확인한다. 실패가 확정된 건만 `알림톡 재발송`을 사용한다. `결과 미확인` 건은 콘솔 확인 전 재발송하지 않는다.

## 운영 반영 전 확인할 내용

- 실제 키의 Biz Message 발송 권한과 서비스 ID/채널 일치 여부
- 운영 서버 환경 변수 주입과 최신 코드·DB 스키마 반영
- 본인 번호로 두 템플릿의 실제 수신 및 택배사 링크 확인
- 실제 고객을 대상으로 하기 전 발송 과금과 장애 대응 확인

API 근거: [NCloud 알림톡 발송](https://api.ncloud-docs.com/docs/sens-alimtalk-send), [발송 결과 조회](https://api.ncloud-docs.com/docs/sens-alimtalk-get).
