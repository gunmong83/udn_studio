# 유입 → 구매 분석

관리자 트래픽 분석의 기본 탭은 `유입 → 구매 분석`이다. 외부 분석 서비스나 추가 인증키 없이 기존 SQLite/Prisma로 동작한다.

## 측정과 해석

- 방문자는 브라우저 localStorage의 익명 ID, 세션은 탭별 sessionStorage ID로 구분한다. 30분 비활동 후 새 세션을 시작한다. 다른 기기/브라우저를 한 사람으로 병합하지 않는다.
- 새 세션의 첫 유입 페이지와 referrer 도메인, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`를 고정한다. 로그인·결제 제공자에서 돌아왔다고 첫 유입을 덮어쓰지 않는다. 원문 URL 쿼리·검색어·전화번호·배송정보는 이벤트로 저장하지 않는다. 캠페인 이름에도 개인정보를 넣지 않는다.
- 예: `https://studioundesignated.com/products?utm_source=instagram&utm_medium=social&utm_campaign=postcard_2026&utm_content=profile`.
- 상품 조회는 상품 상세 pageview, 담기는 실제 장바구니 쓰기, 결제 시도는 배송정보 검증 후 결제창 요청으로 측정한다. 비로그인 checkout 도착·결제 입력/준비/응답지연·실패 페이지도 별도 관측한다.
- pageview/event ID를 유일하게 저장해 effect 재실행·동일 요청 재전송의 중복을 막는다. 체류 시간은 탭이 보이는 시간만 기록한다. 로그인 유저 ID는 클라이언트 값을 신뢰하지 않고 서버 세션에서 읽는다. 관리자와 봇 방문은 수집에서 제외한다.
- 구매는 클라이언트 이벤트나 성공 페이지 조회가 아니라 NICEPAY 서버 승인 후 주문에 기록된 `paidAt` 및 `paymentStatus=PAID`로 판정한다. 기존 조건부 승인 갱신에서 한 번만 결제 시각을 기록하므로 새로고침/중복 콜백으로 구매가 늘어나지 않는다.
- 주문 생성 때 서버 서명·만료 검증된 HttpOnly `udn_analytics` 쿠키와 요청 세션 ID를 대조해 `Order.analyticsSessionId`를 연결한다. 분석 저장 실패/차단은 쇼핑을 막지 않으며, 연결되지 않은 주문은 연결률에 별도로 표시한다. 서명은 기존 `AUTH_SECRET`을 사용한다.
- 전환율/유입·기기·랜딩 비교는 **선택 기간에 시작된 새 측정 세션 코호트** 기준이다. 해당 세션의 이후 결제도 포함하므로 기간이 지나면 값이 변할 수 있다. `기간 내 결제 완료`는 **결제 시각** 기준으로 별도 집계한다. 서로 분모가 다른 수치를 혼합하지 않는다.
- 경로 도표는 동일 세션 내 방문 → 상품 조회 → 담기 → checkout → 결제 시도 → 서버 결제 완료 순서를 통과한 세션만 센다. 저장 장바구니에서 직행·다른 탭의 구매는 전체 전환율에는 반영돼도 전체 경로에서는 빠질 수 있다. 유입·상품의 원인 효과를 증명하는 실험 결과가 아니다.
- 관리자 전용 테스트 상품/관리자 주문 및 현재 환불 상태 주문은 구매 통계에서 제외한다. 결제금액에는 배송비가 포함되고 상품별 매출에는 포함되지 않는다. 환불 후 수치는 변할 수 있다.
- 개선 관측은 충분한 표본이 있을 때의 이탈 구간과 로그인/오류 신호를 제시하는 가설이다. 특히 결제창 응답 지연과 실패 페이지 도착은 최종 미결제를 보장하지 않는다. 실제 결제 기록과 대조한다.
- 과거 방문에는 담기/결제 이벤트와 주문 연결이 없어 새 구매 경로를 소급 복원하지 않는다. 기존 세션은 `measurementVersion=0`, 새 측정 세션은 `1`이다. 새 `paidAt`이 없는 과거 주문도 새 기간 결제 통계에는 포함하지 않는다. 기존 트래픽 탭은 유지한다.

## 적용·검증

1. `web`에서 `pnpm exec prisma generate` 및 `pnpm build`를 수행한다.
2. 로컬 DB는 기존 `scripts/init-local-db.mjs`가 추가 테이블·열을 데이터 삭제 없이 적용한다. 운영은 기존 배포 전 DB 백업과 컨테이너 시작의 `prisma db push --skip-generate`를 따른다. `.env`나 고객 DB를 커밋하지 않는다.
3. `node --test tests/analytics.test.cjs tests/checkout-success.test.cjs`로 가짜 사용자/임시 DB에서 중복·서명·세션 소유권·서버 구매 집계·코호트·경로 순서·환불/테스트 제외를 확인한다. 실결제·알림톡·메일은 호출하지 않는다.
4. 브라우저에서는 로그아웃 또는 일반 회원으로 캠페인 URL → 상품 → 담기 → checkout을 확인한다. 관리자 로그인 브라우저로 쇼핑하면 분석에서 제외되므로 별도 브라우저/프로필을 사용한다. 관리자 분석 화면에서 새로고침한다.
5. 실구매 검증은 본인 테스트 주문으로 승인 → 주문 연결/paidAt 확인 → 성공 페이지 새로고침 후 주문 수가 늘지 않는지 확인한다. 결제 과금 여부를 확인한 뒤 진행한다.

클라이언트 분석은 광고 차단/브라우저 저장 차단/요청 손실/쿠키 만료에 영향을 받으므로 회계 원장이 아니다. 먼저 유입 연결률을 확인하고, 낮은 표본으로 채널 성과를 단정하지 않는다. 외부 광고 전송/세션 녹화는 추가하지 않았다.
